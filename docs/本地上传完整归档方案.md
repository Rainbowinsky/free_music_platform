# 本地上传完整归档方案

> 范围：本文基于现有实现进行只读审查，给出后续改造方案；本文不包含代码改动。
>
> 目标：让管理员上传其有权使用的本地音乐文件后，稳定地创建或补齐歌曲、歌手、专辑、封面、歌词，并可在主站播放、查看逐行歌词。

## 1. 结论摘要

当前“本地上传”已经可以完成一条基础归档链路：上传单个音频 → 读取内嵌标签 → 缺失时按文件名和网易云检索补信息 → 写入 `songs / artists / albums` → 将音频、封面、歌词保存到 `public/`。

但它还不是“完整音乐包上传”能力。当前只有**一个音频文件**上传入口：

- 不能单独上传 `.lrc` 歌词文件；
- 不能单独上传专辑封面图片；
- 不能批量上传整张专辑；
- 音频格式虽在界面上宣称支持多种格式，但服务端会把原始字节统一命名为 `.mp3`，会造成格式、扩展名和响应 MIME 类型不一致；
- 在线补全只依赖网易云，网易云无版权或缺失时容易无法补全，且缺少管理员确认匹配结果的步骤。

推荐将上传能力升级为“**单曲完整归档包**”与“**专辑批量归档包**”两级流程，并把“音频、元数据、封面、歌词”分别作为可验证的独立输入。音频是唯一必选项；歌词和封面可由文件、内嵌标签或可信元数据源按优先级补齐。

## 2. 当前实现盘点

### 2.1 前端入口与实际可选文件

前端位于 `src/pages/admin/AdminConsole.tsx` 的 `UploadTab`。

- 使用单个 `<input type="file">`，每次只取 `files[0]`；拖入多个文件也只处理第一个。
- `accept` 值为 `audio/*,.mp3,.flac,.m4a,.wav,.ogg`。
- UI 文案明确写了 MP3 / FLAC / M4A / WAV；实际 `accept` 还包含 OGG。
- `accept` 仅是浏览器选择器提示，不能作为后端安全校验。
- 调用 `POST /api/admin/upload`，`FormData` 中只携带字段 `file`。

### 2.2 后端上传与解析流程

接口位于 `server/src/routes/admin.js`：

- `multer.memoryStorage()`：整个文件先进 Node.js 内存；
- 单文件字段：`upload.single('file')`；
- 文件大小上限：60 MB；
- 管理员权限：需要 `adminRequired`；
- 当前无扩展名、MIME、文件签名、实际可解码性、码率或时长等服务端准入校验。

归档函数位于 `server/src/music/importer.js` 的 `archiveUploadedFile()`，执行顺序如下：

```text
上传音频
  → music-metadata 读取标签与内嵌封面
  → 标题/歌手缺失时，从文件名猜测
  → 用网易云官方搜索匹配歌曲
  → 回填专辑、歌手、时长
  → 没有内嵌封面时，尝试下载网易云封面
  → 匹配到歌曲时，尝试下载网易云 LRC
  → 歌手、专辑自动创建或复用
  → 音频、封面、歌词落盘并写入 MySQL
```

### 2.3 当前支持的元数据来源与优先级

| 信息 | 当前优先级 | 备注 |
| --- | --- | --- |
| 歌名 | 内嵌标签 → 文件名猜测 → 网易云匹配 | 可能为空，现状不强制校验 |
| 歌手 | 内嵌标签 → 文件名猜测 → 网易云匹配 | `artist_text` 会保留字符串，但歌手实体只取 `/` 前第一位 |
| 专辑 | 内嵌标签 → 网易云匹配 | 无法填写或回填发行年份 |
| 时长 | 音频容器解析 → 网易云匹配 | 未做“文件实际时长与匹配曲目时长”的强校验 |
| 封面 | 内嵌图片 → 网易云封面 | 不支持单独上传图片；不会覆盖已有内嵌封面 |
| 歌词 | 网易云 LRC | 不支持上传外置 `.lrc`；无网易云匹配即通常没有歌词 |
| 音频 | 上传文件本身 | 不转码、不验证可播放性 |

### 2.4 当前落库、播放和歌词链路

- 音频保存至 `public/music/`；封面保存至 `public/covers/`；歌词保存至 `public/lyrics/`。
- `songs` 表保存相对地址：`src`、`cover`、`lrc`；歌手和专辑自动通过 `findOrCreateArtist()`、`findOrCreateAlbum()` 建立。
- 主站从 `/api/library/songs` 读取曲库；播放器把 `song.src` 赋给单例 `HTMLAudioElement`；歌词页请求 `song.lrc` 并按 LRC 时间标签逐行解析。
- 所以要实现完整体验，最终必须具备：有效音频 URL、可显示封面 URL、带时间标签的 LRC URL，以及正确关联到 `artists / albums / songs` 的元数据。

## 3. 现在能上传什么，应该上传什么

### 3.1 现状下可尝试上传的音频

界面选择器提示支持：

| 格式 | 当前可选择 | 当前解析 | 当前播放可靠性 | 结论 |
| --- | --- | --- | --- | --- |
| MP3 | 是 | 通常可读取 ID3 和内嵌封面 | 相对可用 | 当前唯一相对稳妥的选择 |
| FLAC | 是 | `music-metadata` 通常可读 Vorbis 标签和封面 | 不可靠 | 原始 FLAC 会被保存为 `.mp3` 文件名 |
| M4A / AAC | 是 | 通常可读 MP4 标签和封面 | 不可靠 | 原始容器会被保存为 `.mp3` 文件名 |
| WAV | 是 | 标签和内嵌封面经常不完整 | 不可靠 | 原始 WAV 会被保存为 `.mp3` 文件名 |
| OGG | 选择器允许 | 取决于容器与浏览器 | 不可靠 | 原始 OGG 会被保存为 `.mp3` 文件名 |

**重要问题：**`persistSong()` 当前固定以 `${source}-${sourceId}.mp3` 写入任意上传内容。因此，上传 FLAC、M4A、WAV 或 OGG 时，文件内容没有变成 MP3，却会被伪装成 `.mp3` 路径；静态服务通常会据扩展名给出 `audio/mpeg`。这会导致部分浏览器无法解码、播放器失败，且难以排查。

### 3.2 现状下“完整归档”的最小上传建议

在不改代码的前提下，为提高成功率，建议管理员准备：

1. **一首 MP3 音频文件**，建议文件名为 `歌手 - 歌名.mp3`；
2. 尽量写好 ID3 标签：
   - Title（歌名）
   - Artist（歌手）
   - Album（专辑）
   - Album Artist（专辑歌手，可选）
   - Track Number / Disc Number（当前不会落库，但便于后续升级）
   - Date / Year（当前不会落库）
3. 尽量将专辑封面嵌入 ID3 的 APIC/Picture 字段；
4. 若需要逐行歌词，当前只能依赖网易云匹配成功并返回 LRC；不能随音频上传自备歌词。

也就是说，**当前只需要上传一个音频文件**。专辑封面可以内嵌在音频标签中；歌词没有本地文件上传通道，只能走在线补齐。若网易云没有该歌曲或无法匹配，当前流程可能仍能入库并播放，但会没有在线歌词和在线封面补全。

## 4. 推荐的目标上传模型

### 4.1 单曲完整归档包

建议把上传表单升级为以下字段：

| 字段 | 是否必填 | 推荐格式 | 用途 |
| --- | --- | --- | --- |
| 音频文件 | 必填 | MP3、M4A、FLAC、OGG、WAV | 播放源；服务端按真实格式保存或转码 |
| 歌词文件 | 可选 | `.lrc` UTF-8 | 优先用于逐行歌词，覆盖在线补全 |
| 封面文件 | 可选 | JPG、PNG、WebP | 优先作为专辑封面，覆盖内嵌封面 |
| 歌名 | 可选但建议填写 | 文本 | 作为标签缺失时的人工兜底 |
| 歌手 | 可选但建议填写 | 文本 | 作为标签缺失时的人工兜底 |
| 专辑 | 可选 | 文本 | 决定归档进已有或新建专辑 |
| 年份、曲序、碟号 | 可选 | 数字/文本 | 让专辑页具备正确排序和信息 |
| 在线匹配确认 | 可选 | 候选选择 | 仅在需要补元数据时使用，不能静默覆盖人工信息 |

推荐的字段优先级：

```text
人工明确填写 > 同次上传的附属文件 > 音频内嵌标签 > 已有曲库同一专辑信息 > 可信元数据匹配 > 文件名猜测 > 空值
```

### 4.2 专辑批量归档包

第二阶段再提供“整张专辑”工作流：

```text
选择多个音频文件 + 一个可选 cover.jpg + 多个同名 .lrc
  → 解析每首音频标签
  → 生成可编辑预览表格
  → 管理员一次确认专辑名称、主艺人、年份、封面
  → 校验曲序、重复项、格式与歌词同步
  → 原子化或可恢复地批量入库
```

建议默认的文件配对规则：

```text
01 - 歌名.flac
01 - 歌名.lrc
cover.jpg
```

同名 `.lrc` 自动配对同名音频；`cover.jpg/png/webp` 作为整张专辑默认封面；单曲级内嵌封面可选择保留或被专辑封面覆盖。

### 4.3 统一规范化后的归档产物

为了浏览器播放与长期维护稳定，建议制定单一媒体规范：

- **推荐存储音频：MP3 或 AAC/M4A**，并保留真实扩展名与真实 Content-Type；
- 若要支持无损存储，保留 FLAC 原件，同时为 Web 播放生成 MP3/AAC 派生文件；
- 封面统一生成 WebP/JPEG 缩略图，同时可保留原图；
- 歌词统一转 UTF-8 LF 换行的 `.lrc`，保留原始文本与解析状态；
- 用 SHA-256 记录音频内容哈希，避免同一文件重复写盘。

## 5. 推荐的目标流程

### 阶段 A：预检，不写入

1. 接收音频、可选 `.lrc`、可选封面和表单字段；
2. 根据文件魔数而不是扩展名验证真实媒体类型；
3. 解析音频容器、码率、时长、标签、内嵌封面；
4. 验证音频是否可解码，验证大小、时长、封面尺寸和歌词编码；
5. 按优先级合并元数据；
6. 如信息不足，再向可信元数据源请求候选；
7. 将候选与差异返回给前端预览，等待管理员确认。

### 阶段 B：管理员确认

页面应显示：

- 最终歌名、歌手、专辑、年份、曲序、时长；
- 封面预览及来源；
- 歌词预览、有效时间标签行数、首尾时间和与音频时长的偏差；
- “新建歌曲 / 补齐现有无音源歌曲 / 发现重复”三种处理结果；
- 在线匹配候选及置信度，人工选择后才应用；
- 许可证、来源或用户确认信息（适用于用户有权上传的文件）。

### 阶段 C：提交和可恢复写入

1. 写入临时目录；
2. 完成所有校验和数据库事务准备；
3. 将媒体原子移动至正式目录；
4. 在事务内创建/更新歌手、专辑、歌曲与媒体记录；
5. 失败时清理临时文件或保留可恢复任务；
6. 返回歌曲 ID、最终路径、缺失资源和警告。

## 6. 现有问题清单与解决方案

### P0：会影响播放正确性的阻断问题

| 问题 | 现状证据 | 风险 | 解决方案 |
| --- | --- | --- | --- |
| 任意格式固定写成 `.mp3` | `persistSong()` 固定生成 `*.mp3` | FLAC/M4A/WAV/OGG 内容与扩展名/MIME 不符，可能无法播放 | 保存真实扩展名和 MIME；或在服务端转码后才命名为 MP3 |
| 服务端没有真实文件校验 | 上传仅 `multer` 内存接收，`parseBuffer` 失败后仍继续 | 非音频、坏文件可能以“可播放”入库 | 做魔数、容器解析、最小时长、可解码性校验；失败必须拒绝入库 |
| 60 MB 全量进内存 | `memoryStorage()` + 60 MB 上限 | 并发时可造成 Node 内存压力 | 改为受控磁盘临时目录或流式上传；增加并发、速率与总量限制 |
| 上传后直接标记 `playable=true` | `archiveUploadedFile()` 固定传入 | 实际无法解码时前端仍显示可播放 | 预检通过并在服务端获取媒体信息后才设为可播放 |

### P1：会造成数据错误或无法补齐的问题

| 问题 | 风险 | 解决方案 |
| --- | --- | --- |
| 只接收第一个文件 | 无法上传封面、歌词、整张专辑 | 支持 `audio`、`cover`、`lyrics` 多字段；第二阶段支持多音频批量 |
| 无外置 LRC 通道 | 本地完整资源无法脱离网易云 | 支持上传 UTF-8 `.lrc`；优先于在线歌词 |
| 无独立封面通道 | 无内嵌封面的音乐只能依赖在线源 | 支持 JPG/PNG/WebP 上传、裁剪和缩略图生成 |
| 在线补全只依赖网易云 | 网易云无版权或资料缺失时补全失败 | 接入可缓存的多源元数据策略；至少提供管理员手工填写和候选确认 |
| 在线匹配可能只按标题命中回退 | 同名歌、翻唱、不同版本可能错配 | 使用“标题 + 歌手 + 时长 + 专辑 + ISRC”评分，并要求低置信度人工确认 |
| 上传不能补齐现有“仅元数据”条目 | 已建档曲目会被去重跳过，音频无法附加 | 增加“补充媒体到现有歌曲”模式，按 `song.id` 显式关联 |
| 标签空值仍可写入 | 空歌名/错误归档污染曲库 | 提交前强制校验歌名、至少一位歌手，或要求管理员补齐 |
| 专辑年份、曲序、碟号未保存 | 专辑展示和排序不完整 | 扩展 `albums` 和 `songs` 字段，按 `disc_no / track_no` 排序 |
| 多歌手被压缩为文本 | 合作曲无法按多位歌手检索 | 后续引入 `song_artists` 关联表，保留角色和顺序 |

### P2：体验、运维和安全问题

| 问题 | 风险 | 解决方案 |
| --- | --- | --- |
| 没有上传预览与人工修正界面 | 错误匹配只能入库后再编辑 | 增加“解析结果 → 编辑确认 → 提交”两步式 UI |
| 没有进度、取消、重试、任务记录 | 大文件失败状态不透明 | 上传纳入 `import_tasks`，使用任务状态或 SSE 返回进度 |
| 只按歌名/歌手去重 | 同名不同版本误判，或无法识别同文件 | 组合内容哈希、时长、版本信息、外部 ID 和人工决策 |
| 封面格式和尺寸缺少限制 | 超大图占用资源、异常文件混入 | 校验图片签名、最大像素和文件大小；生成标准缩略图 |
| LRC 没有质量检查 | 纯文本、错误编码、与音频不同步仍可能显示异常 | 校验 UTF-8、有效时间标签数、首尾时间、`[offset:]`；展示预览和告警 |
| 前端 LRC 解析较基础 | 不支持多轨翻译、逐字歌词等 | 保留原始 LRC，先支持标准时间轴；复杂格式作为后续扩展 |
| 文件缺少内容哈希和来源记录 | 无法审计、去重和定位损坏资源 | 保存 `sha256`、原始文件名、上传者、上传时间、媒体 MIME、来源说明 |
| 缺少恶意文件防护 | 管理员账号被滥用时可能污染存储 | 限制 MIME/魔数、扫描、频率、并发、存储配额；媒体目录不可执行 |

## 7. 数据模型建议

在保留现有 `songs / albums / artists` 的基础上，建议逐步补充：

### `songs` 建议字段

- `media_mime`：真实 MIME；
- `media_ext`：真实扩展名；
- `media_sha256`：文件内容哈希；
- `original_filename`：原始上传文件名；
- `track_no`、`disc_no`；
- `isrc`：可选的录音唯一标识；
- `metadata_status`：完整、待确认、缺歌词、缺封面等；
- `lyrics_source`、`cover_source`、`metadata_source`；
- `uploaded_by`、`uploaded_at`。

### `albums` 建议字段

- `year`（现有字段已存在但上传流程未写入）；
- `album_artist`；
- `cover_sha256`；
- `cover_source`。

### 新建 `media_assets`（推荐）

用于将单个歌曲与音频、封面、歌词分离管理：

```text
media_assets
  id
  song_id
  kind: audio / cover / lyrics
  path
  mime
  extension
  sha256
  size_bytes
  source_type: upload / embedded / metadata / generated
  source_url
  created_at
```

这样可以保留音频原件和转码产物、追踪封面来源，也便于安全删除和重建缩略图。

## 8. 分阶段实施建议

### 第 1 阶段：修正单文件上传基础能力

目标：让“上传一首歌”可靠可播放。

1. 后端做真实音频类型校验；
2. 保留真实扩展名/MIME，或明确统一转码；
3. 音频解析失败时拒绝提交；
4. 强制歌名和歌手完整，提供编辑确认；
5. 增加内容哈希、原始文件名和上传任务记录；
6. 支持把音频附加到既有“仅元数据”歌曲，而不是一律跳过重复项。

验收：MP3、M4A、FLAC 各上传一首后，均能在目标浏览器播放、显示正确时长，重新加载后路径有效。

### 第 2 阶段：补齐歌词和封面

目标：脱离在线源也能完成“音频 + 封面 + 同步歌词”。

1. 前端改为多字段上传：`audio`、`cover`、`lyrics`；
2. 支持 `.lrc` UTF-8 文件和 JPG/PNG/WebP 封面；
3. 增加封面/歌词预览与质量校验；
4. 明确优先级：人工上传文件高于内嵌标签和在线补全；
5. 在线补全改为“候选确认”，不静默覆盖人工资料。

验收：断网状态下，上传 `song.mp3 + song.lrc + cover.jpg` 后仍能完整创建并在歌词页逐行显示。

### 第 3 阶段：整张专辑批量归档

目标：支持一次上传多首歌曲并规范地关联同一专辑。

1. 支持多音频、目录式拖放或 ZIP 解包（ZIP 应放在后续阶段，先避免复杂安全面）；
2. 根据同名规则匹配 `.lrc`，按曲序解析排序；
3. 表格化预览、批量编辑专辑名/年份/封面；
4. 可恢复任务、逐首错误提示和重试；
5. 在数据库中保存曲序、碟号、媒体哈希。

验收：一张 10 首专辑可一次入库，专辑页按正确曲序显示，每首有独立歌词且共用专辑封面。

### 第 4 阶段：元数据与资源治理

目标：提升匹配质量、可追溯性和长期维护能力。

1. 多源元数据适配与缓存；
2. ISRC/时长/专辑/歌手联合匹配；
3. 多歌手关系表；
4. 原始文件与转码文件的派生关系；
5. 存储配额、文件扫描、告警与后台清理工具。

## 9. 推荐管理员操作规范（改造前）

在现有版本继续使用时，建议遵循以下规范以降低失败率：

1. 上传前优先使用嵌入完整 ID3 标签和专辑封面的 MP3；
2. 文件名使用 `歌手 - 歌名.mp3`，避免只有序号或无意义名称；
3. 不要依赖当前版本上传 FLAC、M4A、WAV、OGG 后一定能播放；它们存在扩展名被写成 `.mp3` 的缺陷；
4. 需要歌词时，确认网易云能检索到相同录音版本；否则当前版本无法导入自备 `.lrc`；
5. 已通过“仅元数据入库”建立的歌曲，当前版本不能直接用上传功能补音频，建议先等待“补充媒体到现有歌曲”能力上线；
6. 上传完成后到主站实际试听并进入歌词页检查，不要只以管理台“已归档”提示作为成功标准。

## 11. 最终建议

不要把“上传成功”定义为“文件已写入磁盘”，而应定义为：

```text
音频可在目标浏览器实际播放
+ 歌名/歌手/专辑归档正确
+ 封面可显示
+ 歌词可解析且能随进度滚动（如提供）
+ 重复项、来源和文件哈希可追溯
```

最优先应修复真实格式保存和服务端媒体校验；然后增加 `.lrc` 与封面上传、预览确认、为现有无音源条目补音频的能力。这样即使在线音乐平台没有版权或没有元数据，也可以完全依靠管理员持有的本地音频、封面和歌词文件完成完整归档。
